# Authoritative scope and decisions
Original brief is reference/WORK_TASK.md. This document makes chosen implementation policies explicit; additions are not represented as original requirements.

## Required behavior
Python REST API, relational database and migrations. Login required for all actions except login. Clients create requests, see only their own, accept/reject their own delivered requests. Operators see all requests, import metadata, assign episodes and perform staff transitions. Admins have operator powers plus create/deactivate users and change roles. An administrator cannot accept a client's request. Seed users from seed/users.json with hashed passwords.
Episode fields: episode_id, robot_id, task_name, recorded_at, duration_seconds, operator_name, quality good/usable/bad. Import messy CSV safely and repeatably; clear row-level reporting. Request fields: owner, task_name, episodes_requested, deadline, notes, status. Status workflow: submitted -> in_progress -> delivered -> accepted OR rejected -> in_progress. Persist actor/time for every transition.
One active request assignment per episode; only good/usable episodes; delivery requires at least episodes_requested assignments. Analytics for date range: daily episode count per robot, request counts by status, median submission-to-delivery time, top five tasks by good episodes. Aggregate in PostgreSQL. Authenticated /health and JSON access logs with method/path/status/duration/user. Small functioning client/operator UI. One-command clean startup and tests. README and 1–2 page NOTES. Incremental Git commits.

## Chosen policies
Create-only import: never silently overwrite an existing episode. Normalize episode IDs uppercase, robot IDs/task names/quality lowercase and trim/collapse whitespace. Existing identical ID/content -> duplicate skip; differing content -> conflict skip. First valid occurrence wins; report this order dependence. Known robots only, from seed README. Reject missing required metadata including recording operator name. Allow finite positive decimal duration <=3600 seconds; cap is our policy. Reject invalid dates and future recording timestamps. Interpret naive dates as UTC; accept ISO including Z, YYYY-MM-DD HH:MM:SS, and DD/MM/YYYY HH:MM. Task names may contain quoted commas. Record these decisions in NOTES.
Match normalized episode task to request task during assignment (extra policy). Allow assignment/removal only in in_progress. Rejected requests must restart work before changes. Accepted/delivered assignments remain reserved. No automatic release; no deletion of accepted requests. Record assignment actor/time too. Status history visible to staff for all and clients for their own. Request creation also creates a submitted history entry.
Request count integer 1..100000. Task 1..120 characters, notes <=4000, deadline valid date not earlier than current Kigali date on creation. No client override of owner/status. No request editing in MVP. Roles are mutually exclusive. Prevent deactivation/demotion of the last active admin and self-deactivation. No public registration.
Stretch: per-assignment simulated export jobs with automatic retry and UI status. Delivery still uses assigned count only; export completion does not gate delivery, explicitly an MVP demonstration policy. No video artifacts, URLs or download buttons.

## Analytics semantics
Inclusive calendar dates start/end, interpreted as UTC bounds [start midnight, end+1 midnight). Episode metrics filter recorded_at. Request counts use requests created in the interval, grouped by CURRENT status. Median uses requests FIRST delivered in the interval, measuring created_at to first delivery; later rework does not reset it. No delivered requests -> null, not zero. Return these semantics in API metadata and README. Range <=366 days; invalid bounds ->400. Staff only, no cross-client analytics disclosure.

## Out of scope
Real video uploads/storage/downloads, email sending, OTP/2FA, billing, registration, real-time SSE/WebSockets, cloud deployment during core build, multi-tenant organizations as authorization boundaries. Background job is the selected bonus. Import via CLI meets the brief; also provide upload UI/API as requested by user.
